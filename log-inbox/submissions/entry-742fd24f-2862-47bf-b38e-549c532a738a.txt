Architecture decisions already settled:
- Commission: adopt AzurPilot's planner as the canonical commission chooser rather than keeping the ALAS greedy chooser. LLM/supervisory policy may set value preferences; deterministic commission scheduling executes them.
- Task priority configurator: skip. Maintain scheduler priority in the fork; expose a narrow structured reprioritization control later only if needed.
- App-level NTP: skip. Trust synchronized Oracle host time; use monotonic clocks for elapsed durations/timeouts.
- Long-idle shutdown/warm-up: keep capability conditionally. Initially keep ReDroid alive and measure runtime stability/resource use; allow stopping Azur Lane during long idle. Deeper ReDroid shutdown can be enabled later if measurements justify it. Browser/manual access is a wake condition.
- Lifecycle ownership: ALAS must not privately own VM/game lifecycle. Build a shared AL Cloud lifecycle service for start/stop/restart ReDroid, start/stop Azur Lane, and lifecycle state.
- Watchdog/recovery: adopt AzurPilot's persistent unattended-recovery philosophy but gate destructive/interactive recovery on control ownership. HUMAN or AGENT_MANUAL ownership supersedes automation recovery. Sensitive failures should become blocked/error states awaiting user/agent rather than blindly restarting forever.
- Remote SSH emulator manager: skip as the primary mechanism; direct shared lifecycle control is cleaner for the Oracle/ReDroid topology.
- Device/runtime hardening: selectively reuse generic ADB/health/recovery ideas; do not import Windows/MuMu-specific machinery as architecture.
- Screenshot normalization: adopt and extend. Physical ReDroid framebuffer may be lower 16:9 resolution; normalize screenshots into canonical 1280x720 vision space and retune recognition thresholds where required.
- Coordinate mapping: build a universal canonical-1280x720 to physical-ReDroid input transform.
- Input/control: build one shared control surface used by ALAS automation, future agent manual tools, and browser streaming controller, with explicit single-owner arbitration.
- OCR/image recognition: required. Use the improved AzurPilot OCR architecture where useful and qualify it for CPU-only Oracle ARM64/Linux operation.
- PlayerPrefs/game settings: keep the safer transactional approach, but desired settings remain AL Cloud-configurable.
- Server status: keep/simplify; use the official game gateway directly if reliable.
- OnePush: skip. A future AL Cloud notification mechanism may be added, but notification failure must never block automation.
- Backups: keep/generalize for durable AL Cloud config/state/statistics.
- Debug video recorder: skip as a separate AzurPilot subsystem.
- Resource/account-state cache: keep/expand into timestamped observations with freshness/source metadata.
- Local reward/income statistics and daily summaries: keep as structured local data/dashboard history; no LLM-generated prose summary is required. Add export so the user can inspect income/resource history externally. External telemetry/upload is off by default.
- Packaging/runtime modernization: keep a modern locked environment and useful CI; do not inherit public distribution/CDN/mirroring or runtime self-updating.
- Logging: keep rotation/retention plus structured machine-readable error events.
- AzurPilot memory profiler: use during fork qualification/longevity testing, not necessarily as permanent infrastructure.
- AzurPilot embedded LLM crash analyzer: skip; future supervisory agent can analyze structured failures.
- 4399-specific floating-button handler: skip.
- AzurPilot AI-maintainer documentation tree: do not copy as a separate subsystem; AL Cloud canon is authoritative.
- CI: retain useful import-smoke, generated-artifact consistency and relevant tests.
- Public release/CDN/mirroring: skip.
